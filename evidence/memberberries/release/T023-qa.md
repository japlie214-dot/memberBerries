## Diff Review
- `crates/memb-store/src/lib.rs`: `expand_one_hop` now reads through the `ADJACENCY_TABLE` index and point reads. The index is rebuilt only when `kb_version` moves. `CLAIMS_PER_KNOWLEDGE = 4` caps the claims per knowledge note in both the indexed path and the legacy `expand_from`. Retracted and missing seeds are filtered by `active()`. `full_scan_count` is incremented only in `load_all_notes_locked`. No defect found.
- `crates/memb-rag/src/lib.rs`: `hot_set` checks the in-process cache, then the persisted row, then rebuilds. It embeds only notes whose content-hash key is absent from the document cache. It returns `Ok(None)` when any note cannot be embedded, which makes the caller fall back to lexical search rather than rank a partial set. `fuse(index_is_active=true)` skips loading all notes. The prompt formats on both paths use `server_document_text` / `document_text` and `server_query_text`, which match `DOC_PREFIX` and `QUERY_PREFIX`. No defect found.
- `crates/memb-embed/src/lib.rs`: `document_key` is SHA-256 over length-prefixed (model tag, title, desc), so field boundaries are part of the key. `read_hot_set` rejects short rows, a length mismatch and overflow (`checked_mul`), and returns `None` so the caller rebuilds. Old v1 and v2 cache tables are dropped on write. No defect found.
- Advisory only: `search` and `search_with_server` now call `memb_core::validate_query` instead of the lexical call they replaced. This is a behavior change for empty or oversized queries. It is consistent with the Phase-Coverage text ("Explicit search has its own nonempty/512-byte limits"), so I am not treating it as a defect.
- Advisory only: `hot_set` reads `kb_version` and `fuse` then uses the hot index without re-reading notes. A note retracted between those two reads could appear as a seed. This is a narrow race that the expansion `active()` check does not cover for seeds. It is not a proven crash, security or caller defect.

## Negative Discriminator Tests
These are reasoned from the assertions and were not run as mutations, since I cannot edit the repo.
- Removing the `CLAIMS_PER_KNOWLEDGE` cap: the store test has 6 claims under one knowledge note with `max_total = 8`. Without the cap the result would be 7 notes, and the `assert_eq!(ids, [k, c0, c1, c2, c3])` check and the `1 + CLAIMS_PER_KNOWLEDGE` loop assertion would fail.
- Removing version invalidation in `ensure_adjacency`: after `retract(claims[0])` the test expects exactly 1 full scan and the ids `[k, c1..c4]`. A stale index would produce 0 scans, so `full_scan_count() - before == 1` would fail.
- Removing version invalidation in `hot_set` (keeping the memory hit): after the update the test expects `Rebuilt { embedded: 1 }`. A stale hit would return `Memory` and fail. After `retract(ids[5])` the test expects `hot.len() == 301` and no retracted id, which a stale set would break.
- Removing the content-hash cache lookup in `hot_set`: the test expects `embedded.get() == 301` after the disk reload and `Rebuilt { embedded: 0 }` for the twin note. Re-embedding would fail both.
- Removing the `index_is_active` shortcut: the scan counter assertions would detect the extra `load_all_notes`.
- Negative inputs: a seed id of 9999 returns an empty set, a claim with an inactive parent does not bring that parent, and `write_hot_set` with mixed dimensions returns an error. A damaged row (`[0u8; 20]`, 3 bytes) reads as `None`, so it is never treated as data.
- Weak point (advisory): `a_loopback_server_without_a_model_identity_is_lexical_only_and_embeds_nothing` asserts only that one lexical result comes back. It would still pass if an embedding were attempted and failed against port 1. The "embeds nothing" claim is therefore not proven by that test alone. The `model` guard is the real protection. This is P2, not blocking.
