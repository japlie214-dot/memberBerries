# Phase coverage and retirement gate

This is a requirements ledger, not a release claim. **Implemented** means the current (workspace 0.11.0) implementation exists; native host verification is separate. **Replaced** means the design intention is addressed differently. **Open** means the phase software and notes must be retained until implementation or an approved disposition.

| Source | Requirement | Current disposition |
|---|---|---|
| Shared design / 1 | Windows-first Rust daemon and CLI, one project memory across clients | **Replaced:** one binary, stdio per client, one OS-serialized redb store. The optional foreground `memb daemon` is a loop you start yourself (see [Operations](Operations.md)); the daemon has no network listener. A per-user scheduled task for it has been registered on the development machine (row 24); memb and the packages never register one themselves. (The separate `memb web` inspector is a read-only loopback HTTP listener you start yourself; see [Inspector](Inspector.md).) |
| Shared design / 1 | 2 GiB Win32 Job Object and kill-on-close; 1200/1550/1750 MiB governor thresholds and bounded redb cache | **Done (T020):** 16 MiB configured redb cache, bounded note/query/frame input; `memb daemon` and `memb mcp` put themselves in a job object with a **job-wide** 2 GiB limit (`JOB_OBJECT_LIMIT_JOB_MEMORY`) and **kill-on-close** (everything the process starts afterwards shares the cap and is stopped with it; tested with a real child). Hooks do not attach, by decision: they are short-lived and bounded (16 KiB messages), and a job per prompt adds cost for no gain. The governor thresholds are wired: every 15 s a governor thread in the daemon and the MCP server reads the process's private memory; from 1550 MiB it drops the embedding model and the query cache, and the daemon pauses background work (routine, curation) at 1750 MiB. The 1200 MiB warn level is only classified. Budget tests cover each threshold. |

Hook latency was measured (see Hooks). Antigravity capture is host-verified (T013); Claude Desktop and Codex are not yet. Explicit search has its own nonempty/512-byte limits. |
| 2 | Managed `llama-server`, CPU ISA selection, EmbeddingGemma prefixes, Matryoshka dimensions, idle unload | **Replaced / partial:** memb never starts a model server. It can call a loopback llama-server you start (`MEMB_EMBED_PORT`) or run EmbeddingGemma 2 (ONNX) in-process (`MEMB_GEMMA_MODEL_DIR`), with optional Matryoshka truncation (128/256/512/768). **Prompt formats (T023):** both paths now use the EmbeddingGemma formats `task: search result | query: <query>` and `title: <title> | text: <description>` (the loopback path used to send raw text, and the in-process path used `title: none` with the title inside the text). Query truncation is **512 tokens** as in the phase document (head 30%, tail 70%; about 2,048 characters on the loopback path). The search tool and the hooks cap the query text at 512 bytes, so a query rarely reaches the limit. **Done (T028):** `memb models install` downloads the pinned model (about 207 MB) with a consent step, size and SHA-256 checks and resume, and memb then uses it with no configuration; see [Install](Install.md#semantic-search-embeddinggemma-2). No model is shipped in the package. **Done (T020):** the in-process model is unloaded after sitting idle (300 s on the CpuLite tier, 600 s on CpuBalanced; the next search loads it again) and at once under memory pressure. A hardware prober (AVX-512 or AVX2+FMA, physical cores, installed RAM) chooses the tier: CpuBalanced needs AVX2/AVX-512, 8 physical cores and 16 GB, otherwise CpuLite. **Done (T030):** the tier also picks the model build and vector width, as Phase 2 does with GGUF quants: CpuLite gets the 4-bit ONNX build (174 MB model data) with 256-wide vectors, CpuBalanced the 8-bit build (314 MB) with 512-wide vectors (ONNX has no Q5; 8-bit is the nearest step up). A machine without AVX2 with FMA (or AVX-512), or with under 8 GB of RAM, is reported as below the floor for a local model, and `memb models install` refuses unless you pass `--variant`. The user-chosen `embeddings.mrl_dim` always wins over the paired width. **Replaced:** there is no GPU tier (the embedder is a CPU-only ONNX model, so a GPU could not be used), no GGUF quantization (the choice is between the two ONNX builds, see the tier text above) and no session-start warm-up (the model loads on first use). The tier sets the idle timer, the model build and the default width; a width in `embeddings.mrl_dim` overrides the default. |
| 2 | Query LRU (256 entries), document embedding cache, quantized project working set and version invalidation | **Done (T023); one departure approved, one rejected (T024):** the knowledge base has a version (`project_kb_version`, it moves with every create, update, supersede, retract and rollback). The i8 hot working set (one vector per active note, per model tag) is kept in this process and persisted in `memory.redb` together with the version it was built at; a search whose version matches reads no notes and embeds nothing, and when the version moved only notes whose content is new are embedded. Document vectors are cached under a SHA-256 key of model identity (with truncation size), title and description (the old note-id key and `DefaultHasher` fingerprint are gone, as are the unused v1 and v2 cache tables); an unchanged note is never embedded twice, whatever its id, and identical text shares one vector. Measured: 1,001 notes at 768 dimensions take 0.78 MB (limit 5 MB, so about 6,400 notes at full width, about 25,000 at 128); an in-process hit takes about 1.3 microseconds; i8 ranking agrees with f32 on 99.5% of top-10 results ([Operations](Operations.md#retrieval-caches)). **Departures:** (1) *approved 2026-11-26 (T024)*: the f32 top-20 rescore is not built, because the i8 ranking already agrees with f32 on 99.5% of the top 10 in the clustered test and a rescore would need f32 vectors on disk (4 times the size) or 20 extra embeddings per query; (2) *rejected 2026-11-26, ticket T029*: the version is checked on every query by opening the database (about 45 ms in a debug build), so a hit is fast but a query is not instant; the user does not accept this cost. A 256-entry query LRU exists only on the loopback server path and only when `MEMB_EMBED_MODEL_ID` is set; the in-process path has no query cache, and a process-static LRU does not help one-shot hook processes, so the query LRU is recorded as **stdio-only by decision (T019)**. Without a backend, search is lexical; the loopback path without `MEMB_EMBED_MODEL_ID` is now lexical too (it used to embed every note on every query). |
| 2 | LanceDB vector ANN + BM25/FTS + hybrid RRF | **Replaced:** hybrid ranking in-process (lexical + quantized vectors, reciprocal rank fusion, lexical fallback); LanceDB is not linked and redb stays authoritative. |
| 2 | One-hop knowledge/claim neighbors with no topic fan-out | **Done (T023):** one-hop expansion from the search hits (a claim brings its parent knowledge, a knowledge note brings at most 4 of its claims, topics bring nothing) through an adjacency index in `memory.redb` (knowledge id to its active claim ids) and point reads, without loading all notes. The index is rebuilt once after the first expansion that follows a knowledge-base change. Checked by `expansion_uses_the_adjacency_index_caps_claims_and_rebuilds_only_after_a_change` (counts full reads of the notes) and `expansion_excludes_inactive_seeds_and_parents_and_obeys_limit`. The IN-edge index replaces a two-way (IN/OUT) index: the OUT edges are the note's own `parents`, which a point read already gives. |

Layer 2 is built (T016): chunk-to-chunk and chunk-to-note links, evidence packets, the three-chunk trigger with a one-hour cooldown, and the curation hash cache. Automatic apply with rollback is built and opt-in (`curator.auto_apply`, T017): per-run limit, no cascade retract, kill switch, audit list and per-proposal rollback of creations, supersessions, retractions and updates. **Open:** unattended-run verification with the real CLIs (T018). Curation from the daemon exists but is off unless `curator.daemon_enabled = true`. |
| 3 | Evidence thresholds: chunk corroboration at 0.72, existing-node match at 0.70, or explicit directive; 30-day staging TTL | **Done for `memb curate`:** chunk-to-chunk 0.72, chunk-to-note 0.70 or an explicit directive qualify a chunk (OR); the `curator_evidence` tool does the same on caller-supplied vectors. ## Departure approvals (T024)

On 2026-11-26 the user approved, in chat, **every departure below except the per-query version check**: "I approve all of them except the 45 ms check". Approval covers the behaviour as built and documented in this wiki; any later change to one of these needs a new approval.

| # | Departure from the phase plans | Reason | Decision |
|---|---|---|---|
| 1 | LanceDB replaced by redb | One embedded store, no second database engine or native dependency | Approved |
| 2 | Managed `llama-server` replaced by an in-process ONNX model or a loopback server you start | memb never starts or supervises a network service; the in-process model needs no server | Approved |
| 3 | HTTP port 7741 IPC replaced by stdio | No listening port, no authentication problem | Approved |
| 4 | Per-type MCP tools replaced by generic tools | Fewer tools for the host to carry; typing is enforced inside | Approved |
| 5 | Three hooks replaced by per-host hooks (no SessionStart or BeforeAgent hook) | Each host exposes different events; only the prompt-submit and turn-end ones are needed | Approved |
| 6 | Secret scrub replaced by reject | A rejected note cannot leak a half-scrubbed secret | Approved |
| 7 | Python sidecar dropped | Zero idle memory and no second runtime to install | Approved |
| 8 | Crate layout and release profile; `install-hooks` replaced by packaged hook files | Packages carry their own hook files | Approved |
| 9 | `session_inspect` is a CLI command, `topic_list` not built | Session text must not be reachable by a model without a human gate | Approved |
| 10 | The 256-entry query LRU lives only in the MCP server | A hook is a new process each time, so a process-static LRU never hits | Approved |
| 11 | Consolidation proposes reversible merges and rewrites no text; only curator-made notes | A merge changes the graph, so it waits for you and can be rolled back | Approved |
| 12 | Markdown mirror is one-way, create-only and flat; no re-embed from edits | Manual edits are never read back into the graph | Approved |
| 13 | No GPU tier and no session-start warm-up | The embedder is a CPU-only ONNX model; a warm-up would load it for sessions that never search | Approved |
| 14 | Curation uses a headless CLI only, with a typed confirmation by default | No direct model APIs or keys inside memb | Approved |
| 15 | No f32 top-20 rescore in retrieval | i8 ranking matched f32 on 99.5% of the top 10; a rescore needs f32 vectors on disk or 20 extra embeddings per query | Approved |
| 16 | The adjacency index holds knowledge-to-claim edges only | The other direction is the note's own `parents`, one point read | Approved |
| 17 | The knowledge-base version is checked on every query by opening the database (about 45 ms in a debug build) | Simplest correct invalidation | **Rejected: ticket T029** |

Query truncation is not a departure: it was changed to 512 tokens at the user's request (see the EmbeddingGemma row above).

## Retirement checklist

1. Verify each intended host with synthetic save → cross-host recall → restart → forget → uninstall. Verify that an import actually makes tools callable. Record host version and package hash.
2. Turn every open requirement into tested behavior or obtain the user's explicit approval for a documented replacement or omission. Retain enough detail to reproduce exact phase behavior without the original files.
3. Have Kanban QA review release evidence and this ledger. Do not pass cleanup on archive shape, unit tests, or partial coverage alone.
4. Only then delete the four specifically named `memd-phase1-windows` through `memd-phase4-windows` directories. Confirm exact paths and keep any unrelated files. Do not clean the entire working directory.
