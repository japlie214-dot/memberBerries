# Operations: daemon, mirror, history and rollback

These commands run on your machine against the local database. None of them starts a network service, and none installs itself. The one exception to "no network" is the model command you configure: `memb curate` (and the daemon, only if you set `curator.daemon_enabled`) runs it, and that program may itself contact a network. The daemon, the mirror, `revisions` and `curate` never change a note; the commands that do are `rollback` and `proposals apply`, each only after you type its confirmation.

## `memb daemon`

```powershell
.\memb.exe daemon [--mirror-out <existing-directory>]
```

A foreground loop for a background process or a scheduled task. **memb does not install the scheduled task itself**; you start the process yourself or run the reviewed installer yourself (see "Scheduled task" below).

- **Start:** applies Windows' 2 GiB job-wide memory cap (with kill-on-close) to itself, starts the memory governor (unloads the idle embedding model; at 1550 MiB drops it and the query cache; at 1750 MiB the daemon pauses the routine and curation until memory falls), reads [config.toml](Configuration.md), opens the store, waits 30 seconds, then checks once a minute.
- **When it runs:** once a day, at or after the configured WIB time (default 15:45, UTC+7), at least `cooldown_hours` (default 20) after the last *successful* run, and in any case once 24 hours (or the cooldown, if longer) have passed since then. The very first run is due immediately.
- **One run at a time:** a run takes a 30-minute lease stored in the database, so a second daemon (or a restart) does not start the routine while a lease is held. The lease is not renewed: a run that takes longer than 30 minutes can overlap a later claim, but it is then refused when it tries to record its result, so it can never mark the routine successful. A clock that moves backwards is refused.
- **A run does, in order:**
  1. **Sweep:** scrolls idle longer than `idle_sweep_hours` (default 24) with at least `idle_sweep_min_messages` (default 45) messages become chunks; the last `scroll.retain_tail` messages stay live. At most 100 scrolls per run.
  2. **Stage:** up to 100 uncurated chunks are recorded as staged evidence. This only marks them; it does not summarize, embed or write notes.
  3. **Mirror** (only if a directory is configured): writes a new `mirror-<timestamp>` folder under it (see below).
  4. **Expire:** staged chunks and pending proposals older than `curator.staging_ttl_days` (default 30) expire (see "Curation").
  5. **Hygiene and consolidation:** scrolls with fewer than `idle_sweep_min_messages` messages that have not changed for 14 days are deleted (this includes the short tail a session keeps after its chunks were saved); chunks, notes and each session's chunk counter are never touched. Then, if an embedding backend is configured, near-duplicate knowledge or claim notes (cosine above 0.88, same kind, both made by curation so both have `source_chunks`) become **pending merge proposals**: an `update` of the survivor (it gains the duplicate's parents and a `merged_from` list; its own text is kept) and a `retract` of the duplicate. A duplicate with child notes is never retracted (the one with children survives; if both have children the pair is skipped). At most 3 merges per run, among the newest 2000 knowledge and claim notes, never the same pair again until one of the two notes changes, and never applied by the daemon: you approve them with `memb proposals apply` and can reverse a merge with `memb proposals rollback`. Notes you wrote by hand are never merged.
  6. **Curate** (only if `curator.daemon_enabled = true`, which is **off by default**): the same as `memb curate` (see "Curation"). This sends private conversation text to `curator.cli_command` with nobody at the keyboard, so it is an explicit opt-in. It only produces pending proposals unless `curator.auto_apply` is on; see "Curation". A model that fails, is missing or is refused (for example when too many proposals are pending) is reported as `curation skipped: <reason>` and does **not** fail the routine: the sweep, staging and mirror already succeeded and the chunks stay staged for the next run.
  7. **Compact:** the last step compacts `memory.redb` (unused pages are returned to the file system; notes, revisions and chunks are unchanged). A failure here does not fail the routine.
- **Success is recorded only if every step through Curate succeeded or was skipped** (a curation problem does not count). After a failure the daemon waits 15 minutes before trying again, because a failed run does not start the cooldown.
- **Messages** go to stderr as one-line status notes (`routine done; swept N, staged M, pruned P thin scroll(s), proposed K merge(s), database A -> B KiB`); they never contain note text.

### Scheduled task

`scripts/install-daemon-task.ps1` (in the source repository, not in the packages) registers a per-user task that runs `memb.exe daemon` at your logon. It replaces the original kit's installer, which Windows would have stopped after three days (the default execution limit) and which had no dry run.

```powershell
.\scripts\install-daemon-task.ps1 -ExePath C:\Tools\memb\memb.exe -WhatIf   # prints the task, registers nothing
.\scripts\install-daemon-task.ps1 -ExePath C:\Tools\memb\memb.exe           # registers it
.\scripts\uninstall-daemon-task.ps1                                         # stops and removes it
```

The task runs as you, interactively and not elevated, with no execution time limit, a second instance ignored (`MultipleInstances IgnoreNew`), up to 3 restarts 2 minutes apart, and `StartWhenAvailable`. An existing task is never overwritten without `-Replace`; `-ExePath` must be an absolute path to an existing `memb.exe`; `-MirrorOut` (optional) must be an existing directory. Verified here: both scripts parse, `-WhatIf` prints the definition and registers nothing, bad paths are refused, and the settings object has `ExecutionTimeLimit PT0S` (unlimited). The installer was run for real once on the development machine (task registered, state Ready, the settings above confirmed with `Get-ScheduledTask`). **Not verified: a run at logon, and a long unattended run.** The task points at a stable copy of `memb.exe`, so rebuilding in the source folder does not collide with a running daemon; to update it, stop the task, replace the copy and start it again.

### Not done yet

- **No scheduled task is installed by memb or by the packages.** Whether the daemon runs unattended on a schedule is your decision.
- **No consolidation or compaction.** Retraction and deletion are logical; the database file is not shrunk.

## Curation: `memb curate` and `memb proposals`

```powershell
.\memb.exe curate --dry-run         # how much text would be sent; sends nothing
.\memb.exe curate                   # ask your configured model command for proposals
.\memb.exe proposals                # list (newest first); --status pending|applied|rejected|expired|applying
.\memb.exe proposals show 3         # the exact action, its sources and the current note
.\memb.exe proposals apply 3        # asks you to type APPLY 3
.\memb.exe proposals reject 3
```

`memb curate` is the only command that starts a model, and only the command you set in `curator.cli_command` (default is Codex with gpt-6-luna at medium reasoning, see [Configuration](Configuration.md)). **It sends private conversation text to that command.** It stages any new chunks and then makes two kinds of model calls: first **summaries** (one call per staged chunk that has none, at most 20 per run, each sending that chunk's text cut at 24 KiB), then **one curation call** with up to about 96 KiB of **evidence packets** (see below; each chunk cut at 12 KiB, with its summary) plus a list of your active notes (id, kind, title). Everything goes to the command's standard input, with `MEMB_INTERNAL=1` in its environment. Run `--dry-run` first to see the chunk count, size and how many summaries it would ask for. The command is run in a dedicated `curator-sandbox` directory under the data directory (created by memb, so the model session starts with no project files; memb does not keep it empty afterwards), without a shell, with a 3-minute limit and a 64 KiB limit on what it may write back (the command and everything it starts run in a Windows Job Object that kills them all: on timeout or overflow, and also when the command exits, so a program it deliberately left running, for example `start /B`, is stopped too; if the job cannot be created memb falls back to `taskkill /T`); its raw reply is never printed or logged (the proposals parsed from it are shown by `proposals show` and the apply preview). Only the first 200 active notes are listed to it, with titles cut to 120 characters.

- **Summaries (Layer 1):** the reply to each summary call must be one JSON object with 1 to 10 bullets (at most 300 characters each) and an optional `explicit_signal` flag (a standing user directive such as "always use"). A reply that cannot be used skips only that chunk, which is asked again next run; a command that fails or cannot start stops the run before anything is recorded for that chunk. The summary and flag are stored on the chunk, once. If an embedding backend is configured (EmbeddingGemma 2 in process, or a loopback server with `MEMB_EMBED_MODEL_ID` set), the **summary only, never the conversation text,** is embedded and the vector is stored on the chunk tagged with the model identity (and truncation size); with no backend the chunk has no vector. Summaries and vectors cover only staged chunks. The vectors feed the links below.
- **Links (Layer 2, no model call):** each run compares the summary vectors of staged chunks with each other (cosine at least 0.72) and with your active knowledge and claim notes (at least 0.70; note vectors come from the document cache, filled as needed). Only vectors of the same model identity are compared. Links are stored in the database and replaced each run for the chunks still staged. With no embedding backend there are no links, and only chunks holding a standing directive can qualify.
- **Evidence packets:** a chunk qualifies for curation only if (1) it links to another staged chunk, (2) it links to an existing note, or (3) it holds an explicit directive (the model's `explicit_signal`, or "remember / always / from now on" style wording in the summary or in your messages). Linked chunks form connected groups, split at 5 chunks per packet, each with up to 10 related notes, the number of distinct sessions, shared entities, and a hint when two chunks disagree on a `key=value` setting. Chunks that qualify by none of the three stay staged until the staging limit.
- **Hash cache:** each packet has a content hash. A packet the model already judged is not sent again until its content or related notes change or the entry expires (`curator.staging_ttl_days`); `curate` reports `packets_already_judged`.
- **When it runs by itself:** the daemon curates after its daily routine, and between routines as soon as three or more chunks are uncurated, at most once an hour. Both only if `curator.daemon_enabled = true`.
- **What the model can propose:** create knowledge, add or supersede a claim, update a note, or retract a note (never with a cascade), each citing chunk ids from the evidence it was sent. A proposal that cites any other chunk, does not parse, or fails validation is dropped (counted as `skipped`). The host, not the model, records the session id of each source. At most 8 proposals are kept per run.
- **At most 200 proposals can be pending.** `memb curate` refuses to send anything while fewer than 8 slots remain; apply, reject or let some expire first.
- **It changes no note.** Valid proposals are saved as `pending` in the database, shared by every process, and listed by `memb proposals`. Only chunks that a saved proposal cites leave staging; chunks the model deferred stay staged until the 30-day limit (their packet is not re-sent while unchanged); if the command fails or its reply is unusable, nothing is recorded and the chunks stay staged for the next run.
- **Applying needs your typed confirmation** of that exact proposal, and works once. `proposals apply` and `proposals reject` refuse to run when `MEMB_INTERNAL=1` is set (the environment the model command gets), so a command that runs shell commands cannot simply approve its own proposal; this is a guard against accident, not a security boundary, because a program can remove an environment variable. Choose a command without tool or shell access (the default Codex command runs read-only). The proposal is claimed before the change is made: the proposal is claimed before the change is made, so a second process or a repeat cannot apply it again. If the change cannot be made as proposed (for example the note changed meanwhile) the proposal is marked `rejected` with the reason printed. A run that is killed between the claim and the result leaves the proposal `applying`; it is never applied twice, and you can `reject` it.
- **Provenance:** a created note, or an updated note, gets `properties.source_chunks` (session and chunk ids), added by memb in the same write as the change; an update keeps the note's earlier sources. A retracted note cannot carry a source, so the record of what supported a retraction is the proposal itself (`proposals show`). `source_chunks` is reserved: a model that sets it is rejected.
- **Staging limit:** chunks staged, and proposals pending, for longer than `curator.staging_ttl_days` (default 30) expire. This happens on every `curate`, on `proposals` (list and apply) and in each daemon routine run. Expiry marks them; **raw chunk text is not deleted**, only no longer offered for curation.
- **Auto-apply (opt-in, `curator.auto_apply = true`):** the Phase 3/4 design, decided as full auto-apply with rollback as the safety net. Each valid proposal is applied right after the run saves it, all kinds, with `source_chunks` stamped, and the store revisions it wrote are recorded on the proposal. Rails: at most `curator.max_auto_edits` (default 5) per run (the rest stay pending); a retraction of a topic, or of a knowledge note that still has active claims, is a cascade and always waits for you; the exact action is secret-checked; `memb proposals pause` stops all automatic applying until `memb proposals resume` (both refuse inside a curation session). `memb proposals audit` lists what memb applied by itself, with the revision ids, and `memb proposals rollback <id>` (typed `ROLLBACK <id>`) reverses every edit of that proposal at once: a created note becomes retracted, a superseded or retracted note is active again, an update is restored. A rollback is refused, changing nothing, if a later edit touched the same note or if it would leave an active note under an inactive parent; undo the later edit first. With auto-apply off (the default) everything above about typed confirmation is unchanged. Proposals applied before this feature recorded no revisions and cannot be rolled back this way (`memb rollback --rev` still undoes single updates).
- **Models and fallback:** the headless model is a command-line program, never a direct API, so memb handles no model credentials (decided 2026-11-25). The default is Antigravity `agy` with gemini-4-hydrogen-medium; if it fails or its quota is used up, memb uses Codex with gpt-6-luna at medium reasoning (`curator.fallback_command`). Both are verified with real runs (agy 1.5.15, Codex CLI 0.156.0): `memb curate` produced a correct summary and `explicit_signal` and an answer memb parsed; the opt-in tests `real_agy` (the shipped defaults) and `real_codex` repeat them. Not planned: a Claude CLI (only Claude Desktop is installed here).
- **Quota handling:** when a model reports its usage quota or rate limit as used up (memb recognises the wording of Codex and agy and reads the wait they name, such as `Resets in 3h28m26s` or `try again at Nov 28th, 2026 9:23 PM` in local time), memb stops calling that model until then. With no time named the wait starts at 15 minutes and doubles up to 6 hours; it never exceeds 7 days. Meanwhile the fallback answers; if every model is waiting, `memb curate` and the daemon stop at once with the time to come back (nothing is lost: chunks stay staged and are curated later), and the "3 uncurated chunks" trigger does not fire. A model that answers again clears its wait. `memb curate --retry-now` forgets all waits and tries anyway. An ordinary failure (not a quota) moves on to the fallback for that call but starts no wait. What a model writes is only matched against these phrases; it is never shown, stored or acted on.
- **Pure headless model:** the host agents are not affected by memb, and the curation model is not affected by your setup. The Codex command runs with `--ignore-user-config`, `--ignore-rules`, `project_doc_max_bytes=0` and `--disable` for plugins, apps, hooks, memories, browser, computer use, multi-agent and more, so it sees only Codex's five built-in skills and core tools (a stock `codex exec` sees about 25 user and plugin skills and 16 connector plugins). Antigravity has no such switches, so `agy` runs with an empty home directory (`curator-home`): its saved sign-in still works and it sees only its 6 built-in skills, not your `coom` and `kanban-board` plugins, their MCP servers or rules. Both run in an empty sandbox directory with `MEMB_INTERNAL=1`. Authentication still comes from the CLI's own login (for Codex, `CODEX_HOME`).
- **Curation rules (the model's prompt):** the model promotes only facts that will still be useful two or more weeks from now and defers test values, one-off scratch experiments and transient task state. Structured data (numbers, enums, file paths, versions, status) goes in a note's properties and is never repeated in its description. A knowledge note's description is never grown: a new fact, constraint or update becomes a claim, and a claim that new evidence contradicts is superseded.
- **Not done:** no Claude CLI is supported or verified. From the daemon curation runs only if you set `curator.daemon_enabled`.

## Obsidian mirror

```powershell
.\memb.exe mirror --out <existing-empty-directory>
```

Writes one Markdown file per active note (retracted and superseded notes get no file) into an **existing, empty directory outside the data directory** (create it first), named `<kind>-<id>.md` in that one flat folder. Each file has YAML frontmatter (`id`, `kind`, `title`, `source_chunks` when the note has curation provenance, and all `properties`) and Obsidian `[[wiki-links]]` in both directions: `## Parents` links to the note's active parents and `## Children` to its active children. It is create-only: it never overwrites, updates or deletes a file and is not a sync; edits made in Obsidian are never imported. The snapshot is checked for credentials first and refused if any are found. A failure part-way can leave partial output, so use a fresh directory each time. The daemon does the same into `mirror-<timestamp>` subfolders.

## Diagnostics

Read-only commands for when something seems off. None of them prints note text or conversation text, except `chunk read`, and none sends anything to a model.

```powershell
.\memb.exe doctor                        # health check, exit code 1 if a core check fails
.\memb.exe inspect session <id>          # <id> or <cli>_<id>, e.g. cc_<session id>
.\memb.exe chunk read <chunk id> [--offset N] [--limit 1-50]
.\memb.exe history [--note <id>] [--limit 1-200]   # the same command as `revisions`
.\memb.exe routine run-now               # one daemon pass now
```

- **`doctor`** prints one line per check: `ok`, `info`, `warn` or `FAIL`. Core checks (`FAIL` makes the exit code 1): the data directory, opening `memory.redb` (which takes the lock), and `config.toml`. The rest are `ok`, `info` or `warn`: the embedding backend you configured (a port is only connected to, nothing is sent; a model directory is checked for its files), whether the curation model and fallback commands can be found on `PATH` without running them (a `.cmd` shim is flagged because memb starts commands without a shell), whether a model is waiting for its quota or auto-apply is paused, Job Object availability, CPU features, cores, RAM, the hardware tier and this process's memory, whether the plugin folder has its hooks file and whether capture or the kill switch is set in this environment, and the state of the optional `MemberBerriesDaemon` scheduled task (a task that points at a program that no longer exists is a warning: reinstall it with `scripts/install-daemon-task.ps1`).
- **`inspect session`** prints one JSON line per match: messages out of `max_messages`, `total_chunks`, `dedup_epoch` (`total_chunks` divided by `scroll.dedup_reset_every_n_chunks`), the ids of the notes injected in that epoch, and memb's own memory use. Exit code 1 if the session does not exist.
- **`chunk read`** prints a bounded page of a captured chunk as JSON. It needs `MEMB_SCROLL_CAPTURE=1` and refuses with `MEMB_NO_MEMORY=1` or in an ignored directory, exactly like the `scroll_chunk_read` tool. The text is untrusted and may be private.
- **`routine run-now`** runs the daily routine (sweep, staging, mirror, expiry, and curation if `curator.daemon_enabled`) immediately, ignoring the time of day and the cooldown. It still takes the lease, so it prints `"ran": false` and exits 1 if the daemon, or another run, holds it.

## Revision history and rollback

Every `remember`, `update`, `supersede` (two revisions: the old and the new note) and `retract` records numbered revisions with before and after images.

```powershell
.\memb.exe revisions                 # newest first, up to 20
.\memb.exe revisions --note 12 --limit 50
.\memb.exe rollback --rev 31
```

- `revisions` prints one JSON line per revision: `revision`, `ts_ms`, `op`, `note`, the fields that `changed` (`title`, `desc`, `parents`, `properties`, `status`) and a `rollback` hint that depends only on the operation type (`update` revisions are eligible for a preview, everything else says "not supported"); the preview can still refuse an eligible one, for example if the note has changed since. **It never prints note text.** The limit is 1 to 200.
- `rollback --rev <id>` shows the exact current note and the note it would restore, then asks you to type `ROLLBACK <id>`; anything else cancels. If you confirm, the restore is applied atomically as a **new** revision (history is never rewritten). If the change is committed but the confirmation line cannot be written (for example the terminal was closed), memb says the rollback was applied and exits 1; run `memb revisions` to see it.
- **`memb rollback <revision>` only reverses single-note updates** (to undo whole auto-applied proposals, including creations, supersessions and retractions, use `memb proposals rollback <id>`, above). Creations, supersessions, retractions and anything that touched several notes are refused, and the command prints the reason (`memb: rollback failed: <reason>`, for example "only single-note updates can be planned; grouped and lifecycle operations require store support" for a creation, supersession or retraction, "revision is stale or current note is missing" after the note changed, or "revision not found"); undo those with the normal tools instead: retract a note you created by mistake, and create a new note to replace one that was retracted or superseded (`supersede` only works on an active claim). A rollback is also refused if the note changed after that revision, if the restored text no longer passes validation, or if its parents no longer exist. A revision can be rolled back once: after that, the note no longer matches its after-image.

## Retrieval caches

Search with an embedding backend keeps three derived structures in `memory.redb`; all of them are rebuilt from the notes, so deleting them loses nothing but time.

- **Knowledge-base version:** a number that moves with every note change (create, update, supersede, retract, rollback). Everything below records the version it was built at.
- **Hot set:** one i8 vector per active note for each model tag (model identity, prompt format and truncation size), stored as one row and also held in memory. A query whose version matches reads no notes and embeds no notes. At 768 dimensions it takes about 780 bytes per note (1,001 notes: 0.78 MB, about 6,400 notes in 5 MB; set `embeddings.mrl_dim` lower for bigger bases). The memory governor drops the in-memory copy under pressure; the next query reloads the stored row. **Building it never blocks a search (T036):** when the set is missing or out of date, a search ranks with the vectors already saved plus lexical search and returns at once; the MCP server (the only process that builds) embeds the missing notes in a background thread, 16 at a time, saving each chunk, so a killed or failed build resumes without embedding finished notes again. Hooks and the CLI leave the build to the MCP server. With the real model, a first search with no index answered in 0.5 s (a blocking build took 33 s for 100 notes), and the search after the build was complete and correct.
- **Document vectors:** keyed by a SHA-256 of the model tag, title and description. After a note changes only that note is embedded again; notes with identical text share one vector. Vectors of notes that were edited are not pruned (about 0.8 KB each at 768 dimensions).
- **Adjacency index:** knowledge note to its active claims, used by one-hop expansion (a claim adds its parent knowledge, a knowledge note adds at most 4 claims). Rebuilt once after the first expansion that follows a change.

Lexical ranking still reads every note once per query; that scan is not cached. Changing the prompt format or the model identity changes the tag, so old vectors are never mixed with new ones and the first query after an upgrade embeds the base once.
