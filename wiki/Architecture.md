# Internals and operating boundaries

## Runtime flow

A host spawns `memb.exe mcp` and sends newline-delimited JSON-RPC over stdin/stdout. Initialization negotiates a supported MCP protocol and tools are unavailable until the initialized notification. Invalid messages get protocol errors; valid tool calls with invalid inputs get an MCP tool error. Frames are held to 64 KiB; oversized lines are drained without storing their contents. Stdout carries only protocol data. Startup failures use a fixed stderr message; if an invalid `config.toml` is the cause, a line naming the setting is printed first (never its value).

Domain checks in `memb-core` enforce bounds and credential rejection before `memb-store` receives a valid note. Each process accesses the same `%LOCALAPPDATA%\memberBerries\memory.redb` (or absolute `MEMB_DATA_DIR`). MCP mode starts no network listener, permanent broker, or external model. The separately started [web inspector](Inspector.md) uses a private, read-only IPv4 loopback listener. The store acquires an exclusive OS file lock in a stable `store.lock` alongside the database for each operation. It waits up to roughly three seconds for contention. The lock is released even when the process exits unexpectedly; do not manually remove the lock file while any client is active.

`redb` handles atomic writes. Notes are stored in one unified graph (topic, knowledge, claim) with a monotonic ID counter and a revision table; the store limits the graph to 50,000 notes. A legacy v0.3 `projects_v1` table is kept untouched as a backup and is verified on every open: if it changes after migration the store refuses access rather than diverge. Retraction removes a note from active queries but does not recycle its ID. Opening the store creates the database and its lock file if they are missing, so `memb search`, `memb mcp` (even before any tool call), `memb web` and the other commands that open it create an empty `memory.redb` on first use; unapproved writes and rejected credentials still store nothing. A disabled hook (capture not opted in) does not open the store and creates nothing. Logical deletion removes the note from active queries; it does not guarantee physical erasure from storage pages, OS backups, or host transcripts.

## Ranking and graph

Lexical ranking splits text into Unicode alphanumeric words, lowercases them, and counts distinct matching terms (three points for title, one for description). When an embedding backend is configured, `memb-rag` also ranks quantized (i8) note vectors and fuses both lists with reciprocal rank fusion (k=60); with no backend, or if it fails, search falls back to lexical ranking alone. Backends: a loopback llama-server (`MEMB_EMBED_PORT`, which sends note text and queries to that local service) or the in-process EmbeddingGemma 2 ONNX model (`MEMB_GEMMA_MODEL_DIR`). Optional Matryoshka truncation: set `MEMB_EMBED_MRL_DIM` to 128, 256, 512 or 768 to keep that many leading components and re-normalize before quantizing; any other value degrades search to lexical-only rather than guessing. The size is part of the vector-cache identity, so changing it never mixes old and new vectors. Hits are expanded by one hop through the graph.

## Privacy and recovery

The OS account and data-directory ACL are the storage boundary; do not point `MEMB_DATA_DIR` at shared, cloud-synced, or untrusted folders. Any trusted process running as that account can potentially access the database. Calls to a host model can send retrieved text to that host, even though memb itself is local. Review text and scope before approving a write; when testing, isolate the data directory.

Close all clients before creating or restoring a directory backup. Do not hand-edit `memory.redb` or copy it while there is an active writer. If it cannot be opened, first confirm the configured directory and write permissions and check for concurrent profile changes. Do not overwrite a damaged store with an empty one; retain the closed store for recovery. There is no scheduled export or compaction guarantee.

## Build pipeline

Crates: `memb-core` (types, validation), `memb-store` (persistence, revisions, migration, lexical ranking), `memb-scroll` (opt-in chat capture, chunking; the hook protocol is described in [Hooks](Hooks.md)), `memb-win` (Windows 2 GiB job cap), `memb-embed` and `memb-rag` (embeddings, hybrid search), `memb-curator` (evidence clustering, approval-gated proposals), `memb-ops` (schedule policy, routine lease, rollback planning, Obsidian mirror) and `memb` (MCP server, web inspector, `config.toml` loader, CLI: `hook`, `daemon`, `mirror --out`, `revisions`, `rollback --rev`; see [Configuration](Configuration.md) and [Operations](Operations.md)). `cargo test --workspace --locked` runs domain and subprocess tests. `cargo build --release --locked` builds the Windows runtime. `python -I scripts/package.py` uses an explicit archive allowlist and emits checksums. Re-running packaging with an identical binary and the same toolchain is deterministic; compiler outputs from unrelated build environments need not match byte for byte.
